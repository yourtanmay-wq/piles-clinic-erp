১ মালিকের মূল নির্দেশ
আমি আমার ক্লিনিক অ্যাপ্লিকেশনের মধ্যে একটি পূর্ণাঙ্গ App Settings System তৈরি করাতে চাই। এই নথিটি আমার অনুমোদিত পরিকল্পনা হিসেবে পড়তে হবে। কাজ শুরুর আগে সর্বশেষ দেওয়া সম্পূর্ণ Project Source পুনরায় অডিট করতে হবে, কারণ Developer বা AI Agent-এর কাছে থাকা source এই পরিকল্পনা তৈরির সময় দেখা source-এর চেয়ে নতুন হতে পারে। কোনো পুরোনো পর্যবেক্ষণকে অন্ধভাবে সত্য ধরে কাজ করা যাবে না।
আমার লিখিত অনুমতি ছাড়া কোনো Code, Database, Design, Role, Permission, Workflow, Build Configuration বা Live Data পরিবর্তন করা যাবে না। প্রথমে Audit Report ও Demo Design দিতে হবে। আমি Demo ও Change List অনুমোদন করার পরেই বাস্তব কাজ শুরু হবে।
২ পরিকল্পনার চূড়ান্ত সিদ্ধান্ত
এই Settings System কার্যকরভাবে তৈরি করা সম্ভব। তবে এটি শুধু কয়েকটি সুইচ বসানোর কাজ নয়। Android ও Web-এর বর্তমান theme, dashboard, role visibility, local cache এবং Supabase access একসঙ্গে সামঞ্জস্য রেখে একটি ছোট Settings Engine তৈরি করতে হবে। নিরাপদ পদ্ধতি হলো Hybrid Architecture ব্যবহার করা: Display settings সঙ্গে সঙ্গে local cache থেকে চলবে, আর প্রয়োজনীয় user preference ছোট একটি cloud record হিসেবে সংরক্ষিত থাকবে।
Settings কখনোই রোগীর তথ্য, Payment calculation, Registration workflow, Follow-up rule, Doctor Visit, RMP commission, Attendance, Salary, Print বা Backup logic পরিবর্তন করবে না। Settings থেকে শুধু Display এবং Shortcut নিয়ন্ত্রণ করা যাবে; Permission বা Data access নয়।
৩ সর্বশেষ Source অডিটের বাধ্যতামূলক নিয়ম
Developer বা AI Agent কাজ শুরুর আগে নিচের বিষয়গুলো সর্বশেষ source-এ নতুন করে যাচাই করবে এবং প্রমাণসহ জানাবে। কোনো নাম, path বা পুরোনো version ধরে নেওয়া যাবে না।
Android-এ বর্তমানে কোনো Settings screen, local preference, session timeout, sync control, crash logging বা backup control আছে কি না
Web-এ Settings page, theme variable, fixed colour, local storage preference এবং session timeout কীভাবে কাজ করছে
Dashboard ও Menu item কোন জায়গায় hard coded এবং কোন জায়গায় role অনুযায়ী দেখা বা লুকানো হয়
একই setting Android ও Web-এ আলাদা মান ব্যবহার করছে কি না
কোনো পুরোনো setting control শুধু মান save করছে কিন্তু বাস্তবে তার consumer বা কার্যকর logic নেই কি না
বর্তমান authentication identity, role source এবং branch source কোনটি সত্য ও সক্রিয়
Supabase schema, RLS, exposed schema এবং current usage pattern Settings-এর সঙ্গে সংঘর্ষ করবে কি না
বর্তমান ভালো চলা feature ও locked design কোনগুলো Protected Area হিসেবে রাখতে হবে
Audit Report-এ প্রতিটি বিষয়ের পাশে Found, Not Found, Partially Working বা Needs Runtime Test লিখতে হবে। Static code inspection দিয়ে runtime behaviour নিশ্চিত না হলে সেটি স্পষ্টভাবে “Runtime Test Required” বলতে হবে।

৬ প্রস্তাবিত Settings Center
Settings একটি স্পষ্ট “App Settings” নামে Master Menu-তে থাকবে। “Backup” নামে Settings লুকানো যাবে না। Backup Center আলাদা এবং পরিষ্কার ঝুঁকি-চিহ্নসহ থাকবে। Settings page-এর উপরে current user, role, branch এবং sync status দেখা যাবে, কিন্তু রোগীর কোনো তথ্য থাকবে না।

৬ ৩ Notification Preferences
এই পর্যায়ে notification delivery logic পরিবর্তন করা হবে না। শুধু বর্তমানে কার্যকর এবং যাচাইকৃত notification category থাকলে তার display preference দেখানো যাবে। জরুরি clinical, payment, security বা approval notification বন্ধ করার option দেওয়া যাবে না। কোনো মৃত বা অসম্পূর্ণ feature-এর জন্য ভুয়া switch রাখা যাবে না।
৬ ৪ Security And Session
Android ও Web-এ session timeout-এর নিয়ম এক জায়গায় সংজ্ঞায়িত হতে হবে। কোন মান Master পরিবর্তন করতে পারবেন এবং কোন মান system minimum বা maximum হবে তা আগে অনুমোদন নিতে হবে। Free Plan-এর advanced Auth session-timeout feature ধরে নেওয়া যাবে না; app-level inactivity timeout প্রয়োজন হলে Android ও Web উভয়ে একই policy অনুসরণ করবে।
Allowed range-এর বাইরে value save হবে না
Active data entry চলার সময় হঠাৎ logout হলে draft loss prevention থাকবে
Security setting পরিবর্তন audit trail-এ নথিভুক্ত হবে যদি cloud policy হিসেবে ব্যবহৃত হয়
Staff কোনো hidden screen বা direct route দিয়ে Master setting পরিবর্তন করতে পারবে না
৬ ৫ Sync And Offline
Settings screen-এ Sync Status, Last Synced Time এবং Sync Now থাকতে পারে। Clinical data sync-এর বর্তমান algorithm এই কাজে পরিবর্তন করা যাবে না। কোনো Auto Sync switch থাকলে সেটি সত্যিই কোন service পড়ছে এবং কী কাজ করছে তা test দিয়ে প্রমাণ করতে হবে; শুধু value save করে রাখা গ্রহণযোগ্য নয়।
৬ ৬ Backup Center
Backup এবং Restore Settings-এর সাধারণ display অংশ থেকে আলাদা থাকবে। Restore-এর আগে বর্তমান backup date, source, affected scope এবং data overwrite warning দেখাতে হবে। এই Settings প্রকল্পে বিদ্যমান Backup বা Restore logic পুনর্লিখন করা যাবে না। শুধু navigation এবং label পরিষ্কার করা যাবে, তাও আলাদা অনুমোদনে।

৮ Settings সংরক্ষণের Hybrid Architecture
৮ ১ Local Cache
Android-এর private local preferences এবং Web-এর protected local browser storage থেকে app প্রথমে theme ও layout পড়বে। তাই startup cloud response-এর জন্য অপেক্ষা করবে না। Local cache corrupt বা missing হলে safe default theme ও default dashboard ব্যবহার হবে।
৮ ২ Cloud Preference
প্রতিটি authenticated user-এর জন্য একটি ছোট preference record থাকবে। এটি patient table, payment table বা clinical table-এর সঙ্গে মেশানো যাবে না। User name বা mobile numberকে একমাত্র security key করা যাবে না; app-এর বর্তমান verified stable authenticated identifier ব্যবহার করতে হবে।

৮ ৪ Conflict Policy
Android ও Web দুই জায়গা থেকে পরিবর্তন হলে server updated time অনুযায়ী newest valid preference জিতবে। Save-এর আগে বর্তমান cloud revision যাচাই করা ভালো। একই সময়ে দুই device edit করলে user-কে “Settings changed on another device” দেখিয়ে Reload অথবা Keep Mine বেছে নিতে দেওয়া যাবে। Clinical data conflict logic এখানে ব্যবহার করা যাবে না।
৯ Supabase Security Design
নতুন preference table exposed schema-তে থাকলে RLS বাধ্যতামূলক
User শুধু নিজের preference select insert update করতে পারবেন
Master policy table থাকলে write শুধুমাত্র verified Master authorization দিয়ে হবে
user metadata claim দিয়ে authorization নয়; verified app metadata বা বর্তমান নিরাপদ role source ব্যবহার করতে হবে
UPDATE policy-তে USING এবং WITH CHECK উভয়টি থাকবে
Frontend বা Android client-এ service role বা secret key রাখা যাবে না
SECURITY DEFINER function শুধু permission error ঢাকতে ব্যবহার করা যাবে না
Migration-এর আগে current Data API exposure এবং grant policy যাচাই করতে হবে
Live migration-এর আগে Security Advisor এবং RLS test চালাতে হবে
RLS policy কপি করে অনুমানভিত্তিক বসানো যাবে না। সর্বশেষ project-এর active authentication model যাচাই করে policy লিখতে হবে। Staff A যেন Staff B-এর preference পড়তে বা বদলাতে না পারে এবং কোনো Staff যেন Master policy লিখতে না পারে—এটি test evidence দিয়ে প্রমাণ করতে হবে।
১০ Supabase Free Plan ব্যবহার সীমা এবং ঝুঁকি
বর্তমান official plan তথ্য অনুযায়ী Free Plan-এ প্রতি project 500 MB database, 5 GB uncached egress, 5 GB cached egress, 1 GB file storage, 50,000 monthly active users, 2 million Realtime messages এবং 200 peak Realtime connections রয়েছে। Settings system-এ Realtime ও Storage প্রয়োজন নেই।
১০ থেকে ১২ জন user এবং প্রতি preference record কয়েক KB হলে database ব্যবহার অতি সামান্য থাকবে। Login-এ একবার read এবং Save-এ একবার write করলে মাসিক egress কয়েক MB-এর মধ্যে থাকার কথা। এটি পরিকল্পনাভিত্তিক অনুমান, live usage measurement নয়। প্রকৃত usage Supabase Usage page থেকে release-এর আগে ও পরে তুলনা করতে হবে।
